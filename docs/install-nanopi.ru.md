# Установка monkey-business на NanoPi R2S

[English](install-nanopi.md) | **Русский**

Подробное пошаговое руководство по запуску VPN-клиента на **NanoPi R2S** (RK3328, aarch64), на
котором **уже работает ImmortalWrt/OpenWrt** и доступен SSH.

Если ImmortalWrt ещё нужно прошить на SD-карту и поднять сеть — сделайте это сначала
(см. документацию ImmortalWrt для `rockchip/armv8` / NanoPi R2S) и вернитесь сюда.

> Везде далее `<router-ip>` — это LAN-адрес вашего R2S (дефолт ImmortalWrt/OpenWrt обычно
> `192.168.1.1`), а команды с префиксом `#` выполняются **на роутере** (через `ssh root@<router-ip>`),
> остальные — на вашей dev-машине в каталоге репозитория.

---

## 0. Предусловия и проверки

На роутере подтвердите платформу и свободное место — geo-базам нужно ~30 МБ, Xray ~25 МБ:

```sh
# uname -m            # ожидаем: aarch64
# cat /etc/openwrt_release | grep -E 'ARCH|RELEASE'
# df -h /             # нужно ~80–100 МБ свободно под xray-core + geo .dat
# nft --version       # fw4/nftables присутствует (в современном ImmortalWrt есть)
```

Если overlay впритык — geo `.dat` качаются в рантайме (не зашиты в пакет), поэтому сам пакет
небольшой, но xray-core + два `.dat` — основная часть объёма.

---

## 1. Установка рантайм-зависимостей

Приложению нужны эти пакеты на роутере:

| Пакет | Зачем |
|-------|-------|
| `xray-core` | прокси-движок |
| `kmod-nft-tproxy` | поддержка TPROXY в nftables (fw4) |
| `rpcd-mod-ucode` | запускает ucode rpcd-плагин |
| `ucode-mod-uci`, `ucode-mod-fs` | доступ к UCI + файловой системе из ucode |
| `curl` | загрузка подписки (захватывает заголовок трафика `Subscription-Userinfo`) |

`scripts/deploy-vm.sh` ставит их автоматически (Раздел 2). Вручную:

```sh
# apk update
# apk add xray-core kmod-nft-tproxy rpcd-mod-ucode ucode-mod-uci ucode-mod-fs curl
```

(На старых сборках с opkg используйте `opkg update && opkg install …`.)

## 2. Деплой файлов приложения

**Рекомендуется: `make deploy`.** Из каталога репозитория:

```sh
npm ci                            # один раз: ESLint + Prettier для проверок JS
make deploy HOST=root@<router-ip>
```

`make deploy` — тонкая обёртка (`scripts/deploy.sh`) над dev-деплоером. Нужна, чтобы заливка на
боевое железо была безопасной и в одну строку: сначала гонит локальные проверки
(`make lint check test-unit`), чтобы не отправить сломанное, затем задаёт device-дефолты
(SSH-порт 22) и передаёт управление `scripts/deploy-vm.sh` для самой заливки. Повторный запуск —
это **обновление**: файлы перетираются, а ваш `/etc/config/monkey-business` (серверы, выбор,
настройки) сохраняется. Опциональные env-оверрайды (префиксом к команде, напр.
`MB_PASS=secret make deploy HOST=…`): `MB_PORT` (SSH-порт), `MB_PASS` (root-пароль, если без
ключа), `MB_SKIP_CHECKS=1` (пропустить проверки, если нет Docker).

Под капотом вызывается `scripts/deploy-vm.sh` — его можно запустить и напрямую для тонкого
контроля (именно его и выполняет `make deploy`):

```sh
MB_VM_SSH_HOST=root@<router-ip> \
MB_VM_SSH_PORT=22 \
MB_VM_SSH_PASS=<root-password> \
  sh scripts/deploy-vm.sh
```

```nu
# nushell
with-env {
  MB_VM_SSH_HOST: "root@<router-ip>",
  MB_VM_SSH_PORT: "22",
  MB_VM_SSH_PASS: "<root-password>"
} { sh scripts/deploy-vm.sh }
```

**По SSH-ключу** (рекомендуется) — авторизуйте его один раз (`ssh-copy-id root@<router-ip>`), затем
полностью опустите `MB_VM_SSH_PASS`; скрипт использует обычные `ssh`/`scp`, поэтому ключ/ssh-agent
подхватываются сами (никакого доп. флага не нужно):

```sh
MB_VM_SSH_HOST=root@<router-ip> MB_VM_SSH_PORT=22 sh scripts/deploy-vm.sh
```

```nu
# nushell
with-env { MB_VM_SSH_HOST: "root@<router-ip>", MB_VM_SSH_PORT: "22" } { sh scripts/deploy-vm.sh }
```

`<router-ip>` — LAN-адрес роутера, обычно `192.168.1.1` (приватный `192.168.x.x`). Проверьте его:
`191.168.x.x` — это *публичный* интернет-адрес, а не ваша сеть, и даст
`Connection closed … / lost connection`.

Что это делает:

- Готовит файлы и копирует их по нужным путям:
  - rpcd-плагин → `/usr/share/rpcd/ucode/monkey-business.uc` (+ `lib/monkey-business/` из `src/`),
  - LuCI-вьюшки → `/www/luci-static/resources/view/monkey-business/`, меню + ACL,
  - `/etc/config/monkey-business` (UCI), `/etc/init.d/monkey-business` (procd),
  - firewall-скрипты → `/usr/share/monkey-business/firewall/`, geo-скрипт → `/usr/share/monkey-business/geo.sh`,
  - watchdog → `/etc/init.d/monkey-business-observer` + observer/recovery/job helpers, сборщик bypass-сетов →
    `ruset.sh`, общая загрузка → `fetch.sh`,
  - прошивка USB-сетевухи → `nicfw.sh` + `firmware/rtl8153b-2.fw`, её watchdog → `nicwatch.sh`.
- **Проверяет рантайм-зависимости** (`xray-core`, `kmod-nft-tproxy`, `kmod-nft-socket`, `ucode-mod-socket`, `coreutils-timeout`, `flock`, `conntrack`, `curl`, ucode/rpcd-модули) и
  ставит недостающие по одному. Если критичный пакет не встал — **деплой падает**: отдать роутер
  без xray молча хуже, чем не задеплоить (обойти осознанно: `MB_ALLOW_MISSING=1`).
- **Ставит прошивку NIC v1** (`nicfw.sh apply`), если найден драйвер `r8152` — см. Раздел 9.
- **Регистрирует cron для NIC и обновления подписок; включает procd observer** и включает `cron` — идемпотентно, повторные деплои их не
  дублируют: `monkey-business-observer` (procd, Раздел 8) и
  `* * * * * …/nicwatch.sh` (страховка от залипания USB-сетевухи, Раздел 9). Заодно включается
  init-скрипт `mb-boothealth` и **удаляется** устаревшая строка `*/5 … boothealth.sh beat`, если
  её оставил старый деплой: этот heartbeat давал 288 принудительных сбросов в сутки в одни и те же
  LBA и убивал SD-карту примерно за две недели.
- **Скачивает geo-базы**, если `/usr/share/xray/{geoip,geosite}.dat` отсутствуют, и собирает
  bypass-сеты в ядре (`ruset.sh build`). Ни то, ни другое не фатально: скачать можно позже из UI, а
  без сетов локальный трафик просто пойдёт напрямую *через* Xray.
- **Сохраняет ваш существующий `/etc/config/monkey-business`** при повторных деплоях (как conffile).
- Доставляет недостающие рантайм-зависимости через `apk` (идемпотентно).
- Перезапускает `rpcd` и проверяет регистрацию ubus-объекта:
  `>> OK: ubus-объект monkey-business зарегистрирован`.

> Сейчас это **единственный** способ установки: `scripts/package.sh` — заглушка, всегда завершается
> ненулевым кодом, так что собирать пока нечего («Альтернатива» ниже — задел на будущее).

> **Не ставьте `MB_UBUS_RESPAWN=1` для реального железа.** Этот флаг (используется только
> `make dev` для QEMU dev-VM) принудительно пересоздаёт `ubusd`/`rpcd` для обхода бага
> эмулятора. R2S это не нужно, и убивать `ubusd` на живом роутере не стоит.

> **Деплой с macOS:** `deploy-vm.sh` уже вычищает AppleDouble-файлы `._*` (`COPYFILE_DISABLE=1`).
> Если когда-нибудь копируете файлы на роутер иначе — убедитесь, что под `/usr/share/rpcd/ucode/`
> не попадают `._*`: rpcd-mod-ucode пытается их скомпилировать и падает.

Предпочтительнее ключевой SSH вместо пароля (`ssh-copy-id root@<router-ip>`), тогда опустите
`MB_VM_SSH_PASS`.

Проверьте, что бэкенд поднялся:

```sh
# ubus call monkey-business status
# ucode -R - < /usr/share/rpcd/ucode/monkey-business.uc   # должно завершиться чисто (проверка синтаксиса)
```

### Альтернатива: установка `.ipk`

Если вы собрали пакет (`make package` с SDK в `MB_SDK_DIR` — ещё допиливается), скопируйте его
на роутер и установите:

```sh
# apk add ./monkey-business_*.ipk        # или: opkg install ./monkey-business_*.ipk
```

## 3. Загрузка geo-баз

Xray не стартует без `geoip.dat` и `geosite.dat`. Проще всего из LuCI:

**LuCI → Services → monkey-business VPN → Dashboard → Update geo databases.**

Качает из Loyalsoldier/v2ray-rules-dat (или ваших кастомных URL), валидирует каждый файл реальным
`xray -test` и устанавливает в `/usr/share/xray/`. Загрузка (~30 МБ) идёт в фоне, а UI опрашивает
статус до завершения.

Из шелла вместо этого:

```sh
# sh /usr/share/monkey-business/geo.sh download
# ls -la /usr/share/xray/geoip.dat /usr/share/xray/geosite.dat
```

## 4. Добавление серверов

В **LuCI → … → Servers**:

- **Подписка:** *+ Add subscription*, вставьте URL провайдера, *Add & fetch*. Серверы импортируются
  (формат определяется автоматически: base64-список или список URI); если скачать не вышло, ничего
  не сохраняется. На свежей установке новая подписка становится активной вместо пустой по умолчанию. Порядок списка — это ваш
  приоритет; перетаскивайте для сортировки, первый сервер — активный. Re-fetch сохраняет ваш ручной порядок.
  Больше одного провайдера: добавьте ещё одну — см. [§10](#10-несколько-подписок).
- **Вручную:** добавьте `vless://…` (Reality/VLESS/XHTTP) или `hysteria2://…` (алиас `hy2://`).

Оба протокола лежат в одном списке — протокол это свойство сервера, поэтому приоритет задаётся
порядком, а failover при обрыве перебирает кандидатов сквозь протоколы.

**Для hysteria2 нужен отдельный клиент.** В feeds OpenWrt его нет, поэтому ставим кнопкой:
**Dashboard → hysteria2 client → Install / update hysteria** (скачивание идёт в фоне, UI опрашивает
статус). Пока клиент не установлен, включение с hysteria-сервером отказывает явно — так задумано:
xray иначе поднялся бы с аутбаундом в мёртвый порт при живом kill-switch, и снаружи это выглядело
бы как «интернет пропал». Из шелла: `sh /usr/share/monkey-business/hysteria.sh install`, проверка —
`… hysteria.sh status`. VLESS/Reality работает без него.

На установку уходит около минуты: сначала собирается контрольная сумма — из релизного `hashes.txt`
со всех зеркал, — и только когда зеркала на ней сошлись, качается сам бинарь на 21МБ. Зеркало,
которое соединение приняло, а данные не отдаёт, бросается через ~20 секунд, а не держит весь
таймаут, так что «installing…» не должно висеть много минут: если висит — у роутера нет маршрута ни
до одного зеркала. Разошедшиеся в сумме зеркала отменяют установку: бинарь исполняется от root, и
непроверяемый нам не нужен.

Клиент поднимается вторым procd-инстансом того же сервиса (живёт и умирает вместе с туннелем),
слушает socks на `127.0.0.1:10810`, а xray ходит в него аутбаундом — маршрутизация, DNS и
kill-switch остаются ровно теми же, что для VLESS.

Токен подписки и UUID серверов хранятся в UCI (только root) и маскируются в UI — держите их вне
логов и issue.

## 5. Настройка маршрутизации (Dashboard + Settings)

**LuCI → … → Dashboard → Split.** Сам сплит живёт на дашборде, потому что меняет не только конфиг
Xray, но и файрвол; панель показывает (✓/✗), что реально включает выбранная пара.

- **Routing mode** — `Bypass local`: ваш локальный регион (RU/CN/IR) и приватные адреса идут
  напрямую, всё остальное — через туннель. Другие режимы: `Only blocked via VPN` (gfwlist) и
  `Everything via VPN` (global). `Only blocked via VPN` берёт готовый список заблокированного
  только для CN (`geosite:gfw` из стандартного geosite.dat Loyalsoldier — учтите это при своём
  geosite URL); для RU/IR/Other в туннель идёт только ваш список **Via VPN**, остальное — напрямую.
  Вне `Bypass local` правила `geoip:<регион> → direct` нет вообще,
  и вместе с ним отключаются bypass-сеты в ядре.
- **Local region** — какой регион считается «локальным» для прямой маршрутизации и для DNS-сплита.
  Выберите **`Other`**, если для вашего региона нет geo-пресета: предопределённой локальной
  geo-категории нет, поэтому сплитом вы управляете сами через custom-списки
  **Direct (bypass VPN)** / **Via VPN** на дашборде. Приватные адреса остаются direct, а всё, что не
  попало в списки, идёт по умолчанию **Routing mode** (bypass-local → туннель, gfwlist → напрямую,
  global → туннель).

**LuCI → … → Settings** — всё остальное; разумные дефолты уже заполнены:

- **Kill-switch** — fail-closed (по умолчанию включён): LAN-трафик к не-локальным назначениям
  дропается, а не утекает напрямую, когда он не несётся туннелем (Xray упал, дыра в правилах или
  не-проксируемый трафик вроде ICMP). Отключите для прямого фолбэка при упавшем туннеле (менее
  безопасно). Локально-региональный и приватный трафик не затрагивается. Реализовано как nftables
  `forward` leak-guard (`scripts/firewall/apply.sh`).
- **Block IPv6** — включён по умолчанию, чтобы клиентский трафик не утекал в обход IPv4-туннеля.
- **TPROXY port** — меняйте только при конфликте (дефолт `12345`).
- **DNS** — `Split` резолвит домены локального региона напрямую, остальное — через DoH в туннеле;
  `All over DoH` отправляет всё через DoH.
- **Anti-DPI** — uTLS-отпечаток + опциональный XHTTP-паддинг.

Кастомные переопределения по доменам/IP (только в сплит-режимах) живут на **Dashboard** в виде двух
списков: *Direct (bypass VPN)* и *Via VPN* — по одной записи в строке: `домен`, `IP/CIDR`,
`geosite:NAME` или `geoip:NAME`.

Нажмите **Save & Apply**.

## 6. Подключение и проверка

**Dashboard → Turn on.** Статус идёт *Starting…* → *Connected*, как только Xray поднимется (UI
опрашивает и показывает ошибки вместо зависания).

Подключение не вслепую: серверы перебираются **по порядку списка**, каждый — на одноразовом
экземпляре Xray, через который должен реально пойти трафик; первый рабочий становится выбранным.
Порядком списка вы выражаете предпочтение — мёртвая запись наверху будет пропущена, а не выбрана.

Но проба не бесплатна: каждый кандидат стоит до ~10 с, перебирается весь список, ограничения нет.
Поэтому при большом списке, где живых серверов мало, *Turn on* может выйти за ubus-таймаут и
показать ошибку вместо аккуратного фолбэка. Не держите в списке заведомо мёртвые серверы или
поставьте надёжный первым.

Проверьте выходной путь:

- **Dashboard → Check exit IP** — пробит ip-api.com *через правила сплита*; вы должны увидеть страну
  вашего VPN-сервера. (Добавьте ip-api.com в список *Direct*, чтобы увидеть свой реальный IP.)
- Из шелла:
  ```sh
  # ubus call monkey-business check_exit '{"domain":"ip-api.com"}'
  # pidof xray && echo "xray running"
  # nft list table inet monkey_business        # ruleset TPROXY присутствует
  # logread | grep -iE 'xray|monkey-business'  # рантайм-логи
  ```
- С **LAN-клиента** (реальный тест — этот бокс ваш шлюз): зайдите на зарубежный сайт и проверьте
  наблюдаемый IP; локально-региональный сайт должен по-прежнему показывать ваш реальный IP.

## 7. Заметки по NanoPi R2S и решение проблем

- **Производительность.** У RK3328 нет аппаратного ускорения AES; реалистичная пропускная
  способность Reality/VLESS ~100–300 Мбит/с. Если ниже — это упор в CPU, а не ошибка конфига:
  тюньте XHTTP/sniffing и предпочитайте Reality более тяжёлым TLS-стекам.
- **Два NIC.** Один Ethernet-порт R2S висит за USB3; убедитесь, что ваш LAN-мост (`br-lan`) — тот,
  на котором клиенты. Firewall перехватывает `iifname "br-lan"` по умолчанию — если ваш LAN-интерфейс
  другой:
  ```sh
  # uci set monkey-business.global.lan_iface=<iface>
  # uci commit monkey-business          # без commit откатится после перезагрузки
  # /etc/init.d/monkey-business restart
  ```
- **Запись в *Direct* будто игнорируется (например, `ping <IP>` с LAN-клиента — timeout).**
  `ping`/ICMP — невалидный тест для вашего *Direct*-списка: перехватывается только TCP/UDP, а ICMP к
  публичному IP дропается kill-switch'ем. Кастомные *Direct*-записи живут только в роутинге Xray —
  обхода на уровне ядра для них нет, — поэтому проверяйте через `curl`/`nc` (TCP) либо добавьте хост
  в *Direct* и подтвердите через **Dashboard → Check exit IP**, а не пингом.
  Исключение — **локальный регион**: его CIDR-диапазоны *лежат* в bypass-сетах ядра
  (`mb_ru4`/`mb_ru6`, включены, когда сплит = `Bypass local` + `Russia`), и leak-guard их пропускает —
  поэтому такие адреса на ping отвечают. Если IP локального региона не отвечает, значит его просто
  нет в сете:
  ```sh
  # nft list set inet monkey_business mb_ru4 | head        # адрес вообще там есть?
  # sh /usr/share/monkey-business/ruset.sh build           # пересобрать сеты из CIDR-списка
  # sh /usr/share/monkey-business/ruset.sh status          # {"state":…,"v4":N,"v6":N}
  ```
  Сеты собираются на этапе деплоя и **автоматически не обновляются** (cron нет, а *Update geo
  databases* трогает только `.dat`-файлы) — пересобирайте вручную время от времени. Пустой сет — не
  утечка: правило Xray `geoip:<регион> → direct` всё равно уведёт такой трафик напрямую, просто
  медленнее.
- **`geo databases missing` при Turn on.** Сначала выполните Раздел 3.
- **Застряло на «Starting…».** Xray упал — `logread | grep xray`. Обычные причины: неверные
  Reality-параметры в записи сервера или TPROXY-порт уже занят.
- **Конфиг переживает reboot/sysupgrade.** `/etc/config/monkey-business` — это UCI; держите его в
  keep-list для sysupgrade (по умолчанию так и есть), чтобы серверы и креды сохранялись.
- **`WARN: ubus-объект не поднялся` сразу после деплоя.** `rpcd restart` иногда оставляет `ubusd`
  живым, но не принимающим соединения (openwrt#9492) — на железе реже, чем в QEMU, но **случается**.
  `deploy-vm.sh` теперь сам детектит недоступный ubus и пересоздаёт `ubusd`+`rpcd`; форвардинг трафика
  не страдает (управление моргает на секунду). Если поймали wedge вне скрипта — восстановите вручную:
  `killall rpcd ubusd; rm -f /var/run/ubus/ubus.sock; /sbin/ubusd & sleep 2; /sbin/rpcd &` — или просто
  `reboot` (сама загрузка на железе нормальная; отдельный boot-hang только у QEMU dev-VM).
- **`apk` или `opkg`.** `deploy-vm.sh` ставит deps тем менеджером, что есть в сборке. Если нет ни того,
  ни другого — поставьте `xray-core kmod-nft-tproxy rpcd-mod-ucode ucode-mod-uci ucode-mod-fs curl` вручную.
- **Direct-трафик (мимо туннеля) тормозит — секунды до первого байта — при живом туннеле.**
  Одна из известных причин: если провайдер не выдаёт IPv6, `odhcp6c` на `wan6` бесконечно
  ретраит, жжёт CPU и вызывает SYN-ретрансмиты на direct-трафике. Выглядит как CGNAT или баг
  маршрутизации monkey-business, но не является ни тем, ни другим. **Сначала подтвердите диагноз** —
  процесс должен заметно крутиться, а лог быть полон ретраев:
  ```sh
  # top -b -n1 | grep odhcp6c        # заметный CPU на якобы простаивающем роутере
  # logread | grep -i odhcp6c | tail
  # ip -6 addr show dev $(uci -q get network.wan.device)   # нет глобального IPv6 = ждать нечего
  ```
  Если картина совпала — отключите IPv6 на WAN. Это выключает IPv6 на WAN полностью: нормально,
  когда провайдер его не даёт, но не делайте этого, если IPv6 у вас реально работает:
  ```sh
  # uci set network.wan6.disabled='1'
  # uci commit network
  # /etc/init.d/network restart
  ```
  Проверено на одном провайдере/устройстве; если симптомы не сходятся с проверками выше — причина
  в другом.
- **Кончилось место на overlay.** Штатный образ ImmortalWrt оставляет небольшой rootfs; xray-core и
  два `.dat`-файла забивают его быстро. Ext4-раздел SD-карты можно расширить прямо с macOS — см.
  [docs/sd-expand-macos.ru.md](sd-expand-macos.ru.md).

## 8. Единое здоровье VPN и recovery

Сервис procd `monkey-business-observer` содержит единственный HTTPS/UDP observer,
асинхронные задания доступности и recovery. Установка включает сервис и удаляет
старую cron-строку watchdog. `watchdog.sh` оставлен как команда проверки статуса;
его прежние environment-настройки больше не управляют recovery.

Раунды начинаются раз в 15 секунд, укладываются в 12 секунд и независимо подтверждают
HTTPS/UDP двумя результатами подряд. Unknown прерывает streak, устаревшие данные
не дают нового диагноза. Отказ только UDP не запускает общее восстановление VPN.
Подтверждённый отказ HTTPS проходит мягкий рестарт, жёсткий рестарт, подтверждённый
failover и полный stop/start; повторные попытки в down имеют backoff 60–600 секунд.
Corporate fallback работает отдельно и учитывает собственный cooldown возвращения.

Routing Apply сохраняет фактически применённый outbound даже после изменения
подписки. При загрузке reconciliation использует его приватный снимок и сохранённые
routing-настройки. Нужны cgroup v2/`cgroup.kill`, nft socket-cgroup и TPROXY,
ucode socket/fs/uci, curl с CA-сертификатами, GNU timeout, flock и conntrack.
Отсутствующая зависимость вызывает явный отказ; успешное копирование файлов
само по себе не квалифицирует платформу.

См. [руководство](routing-availability.ru.md), [локальные проверки, аудит и аппаратные
ворота](routing-availability-acceptance.md). Установка и замеры NanoPi требуют
отдельного разрешения. Статусы лежат в `/tmp/mb-runtime/health.json`, `recovery.json`
и `corporate.json`; приватные definitions/applied-конфиги не включайте в отчёты.
Пользуйтесь публичными status RPC.

## 9. USB-сетевуха RTL8153B: прошивка и watchdog

На R2S весь LAN — это `eth1`, USB3-адаптер RTL8153B на драйвере `r8152` (встроенный `eth0` уходит
под WAN). OpenWrt везёт прошивку `rtl8153b-2 v2 (04/27/23)`, на которой у R2S **зависает TX-очередь**
([openwrt#22130](https://github.com/openwrt/openwrt/issues/22130)): в логе `NETDEV WATCHDOG:
transmit queue 0 timed out`, пакеты теряются, соединения устанавливаются секундами, а под нагрузкой
контроллер уходит в USB-reset и LAN пропадает целиком. FriendlyELEC штатно шлёт `v1 (10/23/19)` —
на ней бага нет.

Деплой чинит это сам: `nicfw.sh apply` кладёт v1 из репозитория поверх пакетной и пинит файл в
`/etc/sysupgrade.conf`, чтобы он пережил `sysupgrade`. Шаг идемпотентный и защищён проверкой:
на чужом железе (нет драйвера `r8152`) он просто ничего не делает.

**Прошивка вступает в силу только после перезагрузки** — драйвер читает её при probe, а
передёргивать USB-устройство прямо в деплое нельзя: деплой идёт по этому же LAN.

```sh
# sh /usr/share/monkey-business/nicfw.sh status
{"driver_r8152":"yes","v1_installed":"yes","kept_on_sysupgrade":"yes"}
# reboot
# ethtool -i eth1 | grep firmware      # после перезагрузки: rtl8153b-2 v1 10/23/19
```

Сверху стоит страховка — `nicwatch.sh` в cron раз в минуту (на случай, если прошивка не применилась
или v1 тоже словит залипание). Тик стоит два чтения sysfs, сетевых проб нет. Реагирует он **только**
на настоящее залипание: `tx_errors` вырос, а `tx_packets` — нет. Одного роста `tx_errors` мало
(счётчик растёт и от безобидных ошибок), иначе watchdog сам ронял бы живой LAN. Эскалация: первый
страйк — передёрнуть линк, дальше — re-bind USB-устройства; если залипание устойчиво, попытки
уходят в паузу, чтобы не ронять LAN каждую минуту и не мешать чинить руками.

```sh
# cat /tmp/mb-nicwatch/state         # tx_errors tx_packets страйки
# logread -e mb-nicwatch
```

## 10. Несколько подписок

**Servers → Subscriptions → + Add subscription** добавляет второго (третьего, …) провайдера: шторка
спрашивает имя и URL и сразу скачивает; неудачное скачивание ничего не оставляет. В строке подписки
*Name*, *URL* (скрыт маской до фокуса) и *Auto-update* правятся на месте — интервал в минутах,
10–120, `0` выключает (на телефоне — переключатель и ползунок). *Fetch* и *Ping* работают с этой
подпиской; корзина после подтверждения удаляет её вместе с её серверами (ручные остаются; при
удалении активной активной становится следующая). Правки копятся до *Save & Apply*; изменённый URL
тогда скачивается заново. *Fetch* и *+ Add subscription* сначала коммитят накопленные правки (*Reset* их
уже не откатит) и блокируют страницу до конца скачивания. Существующий конфиг с одной
подпиской работает как есть — без миграции.

- **Одна подписка активная, остальные — резерв.** Порядок кандидатов: серверы активной подписки
  вместе с ручными (в порядке перетаскивания), затем остальные подписки по порядку. Failover может
  сам уйти в резерв, активная при этом не меняется, и следующее применение снова начинает с неё.
  Сама активная меняется только когда умирает (ниже); обратно — только вручную.
- **Переключение:** при двух и более подписках в **Dashboard → Status** появляется селект
  *Subscription*. Выбор применяется сразу (при выключенном VPN — только сохраняется) и откатывается,
  если применить не удалось. *now via reserve: B* — трафик сейчас идёт через резервную подписку.
- **Мёртвая подписка** (истёк срок или кончился трафик по userinfo провайдера) помечена в селекте и
  не используется как резерв. Если умерла **активная**, в течение минуты активной становится
  следующая живая, а Dashboard показывает *Switched automatically: A expired.* Ручной выбор мёртвой
  подписки отклоняется, пока есть живая, — сначала обновите её (*Fetch*), потом выбирайте.
- **Плашка трафика** показывает подписку, через которую идёт туннель.
- **Пинг:** *Test latency* (все), *Ping* у группы подписки и в строке сервера на Dashboard, *Ping*
  в строке подписки на Servers. В таблице Servers есть своя колонка *Ping* (последние замеры,
  обновляются по *Ping* подписки и *Ping all* над таблицей); *Sort by ping* поднимает самые быстрые
  строки наверх, недоступные и неизмеренные — вниз. Порядок строк — это приоритет подключения, поэтому
  сортировка вступает в силу по *Save & Apply*. Сервер медленнее 1 с или недоступный помечается *auto-off* и
  пропускается при подключении до следующего успешного пинга (результаты — в RAM). hysteria2 (UDP)
  TCP-пингом не измерить — *n/a*. Колонка **Off** в таблице Servers исключает сервер насовсем; в
  списках он остаётся и пингуется.

### Ручная проверка на роутере

Прогонять после деплоя изменений, затрагивающих подписки. `<A>` — id секции активной подписки,
`<B>` — второй (`uci show monkey-business | grep =subscription`). Сначала включите VPN.

0. **Свежий UI.** Откройте Servers обычной перезагрузкой, без сброса кэша. Ожидание: на Servers панель
   *Subscriptions* — по строке на подписку с *Fetch*, *Ping* и корзиной, в шапке *+ Add subscription*, —
   в таблице колонки *Subscription* и *Off*. Форма с кнопками *Fetch subscription* — браузер взял старые скрипты
   из кэша: деплой обязан делать touch `/lib/apk/db/installed`, его mtime входит в `?v=` всех
   скриптов LuCI.

1. **Две подписки.** Добавьте B и нажмите *Fetch*. Ожидание: на Dashboard появился селект
   *Subscription*, таблица серверов разбита на *Active: A* и *Reserve: B*.
2. **Переключение.** Выберите B на Dashboard. Ожидание: страница перезагрузилась подключённой, и

   ```sh
   # ubus call monkey-business status | grep -E '"(active_sub|sub|reserve)"'   # active_sub = <B>
   # cat /etc/monkey-business/active                                            # <B>/<tag>
   ```

   Ручной сервер выше серверов B выбирается первым: тогда в `active` голый `<tag>`, а `sub` = null.
   Проверяйте с ручными серверами ниже или выключенными (*Off*). Перед следующими шагами снова
   выберите A.
3. **Автопереключение.** Сделайте A истёкшей и выключите её обновление (fetch вернул бы настоящий
   срок):

   ```sh
   # uci set monkey-business.<A>.auto_update=0
   # uci set monkey-business.<A>.expire=1
   # uci commit monkey-business
   # sh /usr/share/monkey-business/subupdate.sh      # или дождаться следующей минуты cron
   # logread -e mb-subupdate | tail -n 3
   # uci get monkey-business.global.active_sub       # <B>
   # cat /tmp/mb-runtime/autoswitch.json                           # JSON: from/reason
   ```

   Ожидание: строка лога `подписка <A> expired: активной стала <B>`, плашка на Dashboard
   *Switched automatically: A expired.*, в селекте выбрана B, A помечена мёртвой. Исчерпанный трафик —
   так же: `uci set monkey-business.<A>.total=1` и `uci set monkey-business.<A>.used_download=1`
   вместо `expire`; плашка тогда пишет *ran out of traffic*.
4. **Без повторных записей.** Запустите `subupdate.sh` ещё раз: новой строки `mb-subupdate` нет, и
   `date -r /etc/config/monkey-business` не меняется.
5. **Отказ выбора мёртвой.** Выберите A на Dashboard. Ожидание: предупреждение *Subscription not
   switched: subscription is expired: update it or pick an alive one*; селект возвращается на B.
6. **Вернуть A.**

   ```sh
   # uci set monkey-business.<A>.expire=''
   # uci set monkey-business.<A>.total=''
   # uci set monkey-business.<A>.used_download=''
   # uci set monkey-business.<A>.auto_update=1
   # uci commit monkey-business
   ```

   *Fetch* у A на Servers, выбрать A на Dashboard. Ожидание: плашка пропала (`/tmp/mb-runtime/autoswitch.json`
   удалён).
7. **Сериализация смены подписки.** Займите лок subscription worker и сделайте A истёкшей, как в шаге 3:

   ```sh
   # flock /tmp/mb-runtime/subupdate-switch.lock sleep 60 &          # без flock: mkdir /tmp/mb-runtime/subupdate-switch.lock.d
   # uci set monkey-business.<A>.auto_update=0
   # uci set monkey-business.<A>.expire=1
   # uci commit monkey-business
   # sh /usr/share/monkey-business/subupdate.sh
   # logread -e mb-subupdate | tail -n 1
   ```

   Ожидание: примерно через 30 с — `автопереключение подписки отложено: watchdog занят`, `active_sub`
   по-прежнему `<A>`. Отпустите лок (дождитесь конца `sleep` или `rmdir /tmp/mb-runtime/subupdate-switch.lock.d`) и
   запустите `subupdate.sh` снова — теперь переключается на B. Верните A, как в шаге 6.
   Формулировка лога историческая; активный observer этот лок не использует.
8. **Доступность и Off.** Кнопки доступности запускают асинхронные HTTPS/UDP-проверки,
   включая Hysteria и выключенные узлы. Отказ проверки не меняет ручной Off. Результат
   показывает независимое состояние UDP, возраст и базовую задержку. Sort готовит черновик
   внутри исходных позиций групп; **Apply priority** сохраняет его для следующего подключения,
   работающий VPN сохраняется. Поля узлов применяются обычным потоком конфигурации.
   Правила свежести и отмены описаны в [руководстве](routing-availability.ru.md).
