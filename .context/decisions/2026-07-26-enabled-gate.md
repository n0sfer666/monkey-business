# 2026-07-26 — `enabled` — источник истины для рантайма (гейт в init-скрипте)

## Контекст
Тумблер `monkey-business.global.enabled` был чисто UI-состоянием. Init-скрипт его не читал вовсе:
`START=95` поднимал xray на загрузке независимо от выбора пользователя, а `settings.js`/`dashboard.js`
зовут `config_apply` безусловно — сохранение настроек при выключенном VPN поднимало туннель, пока
дашборд показывал «off». Watchdog при `read_intent=0` за таким туннелем не следит: умри xray —
kill-switch остаётся, LAN заперт, самолечения нет.

## Решение
**1. Гейт в init-скрипте** (`root/etc/init.d/monkey-business`) — рантайм не поднимается без
намерения, кто бы ни позвал:

```sh
mb_intent() {
	[ "${MB_INTENT:-$(uci -q get monkey-business.global.enabled || echo 0)}" = 1 ]
}
```

- **Дефолт 0** — тот же, что у watchdog (`read_intent`) и rpcd (`isTrue(undefined)`). Три разных
  дефолта на одно намерение расходились на обрезанном/старом конфиге: туннель поднят, UI пишет
  «off», watchdog не сторожит.
- **`start_service` при выключенном тумблере делает `flush.sh`**, а не просто `return 1`: rc.common
  зовёт `start_service` внутри `rc_procd`, который шлёт `set` безусловно — при живом xray procd
  получил бы пустые `instances{}` и убил процесс, оставив kill-switch поднятым (LAN заперт). На
  загрузке flush — no-op.
- **`reload_service` выходит ДО `rc_procd`** по той же причине: там пустой `set` снёс бы живой
  инстанс, а `stop_service` (и `flush.sh`) при этом не вызывается вовсе.
- **Гонка «watchdog зовёт `start`, пока пользователь жмёт Off» закрыта самим гейтом**, а не новым
  локом. В rc.common `start()` действительно не зовёт `procd_lock` (в отличие от `stop`/`reload`), но
  `procd.sh` берёт `flock` на fd 1000 ещё при сорсинге (`_procd_wrapper`), т.е. любой вызов
  init-скрипта уже сериализован — проверено на железе (`flock -n` на лок-файле сразу после сорсинга
  возвращает 1). Гейт перечитывает UCI внутри этой секции, поэтому `start`, пришедший вторым, видит
  уже зафиксированный `enabled=0` и не поднимает инстанс. Свой `procd_lock` в `start_service` был бы
  no-op; добавлять его не стали, чтобы код не утверждал несуществующий механизм.

**2. `MB_INTENT=1` — явный обход для пути включения.** `service_toggle` поднимает туннель ДО
commit'а тумблера, поэтому гейт по UCI его бы зарубил. Обход прокидывает только рантайм-`applyConfig`
и только когда `intentOn=true`; `config_apply` из UI обязан упираться в гейт — иначе вернулся бы
исходный баг «настройки молча включают VPN».

**3. Порядок в `serviceToggle`: `applyConfig(json, true)` → `setEnabled(true)`.** Обратный порядок
(рассматривался первым) держал `enabled=1` всё время пробы серверов — до минуты, — и cron-watchdog в
это окно видел intent=1 без xray и поднимал СТАРЫЙ конфиг себе под ноги. `enabled` в ответе —
фактическое состояние: гасить его на ошибке нельзя, xray мог остаться на прежнем валидном конфиге, и
watchdog перестал бы за ним следить.

**4. Намерение должно ПЕРЕЖИТЬ запись.** `setEnabled` теперь возвращает результат `cursor.commit`
(на устройстве — `true`; на read-only rootfs commit не проходит). Не легло — `serviceToggle`
сворачивает туннель (`stopService`) и отвечает ошибкой: иначе оставался бы xray с поднятым
kill-switch'ем при `enabled=0`, за которым не следит никто — watchdog смотрит в UCI, `reload`
отказывается и правила не снимает, дашборд печатает «off». Само состояние всё же достижимо (ручной
`MB_INTENT=1 reload`), поэтому `phaseInfo` в `dashboard.js` получил для него отдельную метку
«Off — tunnel still up» вместо тихого «Off».

**5. Честный ответ наружу.** `configApply` при выключенном VPN возвращает `{ok:true,
skipped:"disabled"}` (не ошибка — настройки сохранены), и все три вызывающих вью (`settings.js`,
`dashboard.js`, `servers.js`) показывают «сохранено, применится при включении» вместо «applied».
Записи в UCI гейт не трогает: `setRouting` пишет списки ДО `configApply`, иначе правки при
выключенном VPN молча терялись бы.

## Проверка (T4 + железо)
- Юнит: `initd_test.sh` (29 ассертов) — гейт, дефолт при отсутствующей опции, flush на выключенном
  `start`, отсутствие flush на выключенном `reload`, обход `MB_INTENT` + пин самой строки-префикса из
  рантайма (опечатка в ней ломала бы каждое включение, а моки читают переменную, не команду);
  `rpcd_test.uc` (33) — `skipped`, порядок apply→setEnabled, `intentOn` только на пути включения,
  сворачивание туннеля при незаписанном намерении. Негативные прогоны: снятие каждого фикса роняет
  ровно свои ассерты.
- Железо: `reload` при `enabled=0` → rc=1, рантайм не тронут; `config_apply` → `skipped`;
  `MB_INTENT=1 reload` поднимает; отсутствующая опция → выключено; `service_toggle on` → pid +
  kill-switch + `probed:true`, выход NL через прокси-инбаунд, RU напрямую; гонка `start` vs `Off`
  (3 прогона) → чистое выключенное состояние; два параллельных `reload` → без дедлока;
  `cursor.commit` возвращает `true`, т.е. проверка намерения не сворачивает исправное включение.
