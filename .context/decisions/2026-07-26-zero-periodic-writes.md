# 2026-07-26 — Ноль периодических записей на rootfs

## Контекст
NanoPi R2S грузится с SD-карты: MBR, один ext4-раздел = rootfs и overlay сразу, `Errors behavior:
Remount read-only`. Устройство стабильно умирало примерно через две недели после каждой переустановки
— и умирало ровно на ребуте: до перезагрузки всё работало.

Два независимых разбора сошлись на одной причине. `boothealth.sh beat` (cron `*/5`) делал `sync` и
переписывал один и тот же 8-байтовый маркер: 288 принудительных сбросов в сутки в узкий фиксированный
набор LBA (голова журнала, блок таблицы инодов `/usr/local`, суперблок). На SD это read-modify-write
целого сегмента FTL (~4 МБ) при 1–2 открытых сегментах. По счётчику записей суперблока выходило
~10 МБ/сутки против 7–9 МБ/сутки от одного `beat` — то есть практически всё, что вообще писалось на
карту, писал `beat`.

Почему износ невидим до ребута: журнал ext4 при штатной работе только пишется, а читается лишь при
монтировании. Отказ приходит на replay следующей загрузки — ядро монтирует root в ro, и роутер
превращается в кирпич. Переустановка образа переносит горячие структуры на свежие физические блоки и
заново заводит те же две недели.

Контрольная точка: passwall держит рантайм в `/tmp/etc/passwall`, лог — в `/tmp/log/passwall.log`,
автопереключение узла — через tmpfs-кэш, а не `uci commit`; v2rayA не использует uci вовсе. Ни в
одном из двух репозиториев нет ни единого вызова `sync`. Поэтому «ImmortalWrt без моего приложения не
умирает, а с ним умирает» — это не про железо и не про прошивку.

## Решение
Периодических записей на rootfs не остаётся ни одной.

- **`beat` удалён** вместе с `do_sync()` и cron-строкой. Деплой ещё и **активно вычищает** строку из
  `/etc/crontabs/root` на уже прошитых устройствах — перестать её добавлять недостаточно.
- **Маркер `/usr/local/.mb-bootstate` остаётся**, но пишется ровно 2 раза за цикл питания: `boot`
  (S11) и `clean` (K99). Единственный `sync` — в `clean`, иначе маркер не дойдёт до карты и следующая
  загрузка объявит ложный unclean.
- **Лог — в syslog под тегом `mb-event`**, а не в свой файл на rootfs. Файл был тем хуже, что
  писался интенсивнее всего именно во время инцидентов, когда watchdog тикает каждую минуту.
  Заодно исчезает самописная ротация и её гонка за общий `.tmp` между watchdog и boothealth.
  Тег отдельный от `monkey-business`: под тем init.d сыплет служебные строки apply.sh/flush.sh на
  каждый старт-стоп, и «последним событием» в UI всегда оказывались они, а не причина отказа.
  `lastEvent()` читает `logread -e mb-event` и вызывается только в фазах down/reconnecting —
  дашборд опрашивает status раз в 5с, а плашка с событием видна только там.
- **`mb-boothealth` переехал на START=13.** Логдемон OpenWrt поднимается на 12, и на прежнем
  START=11 busybox `logger` писал в ещё не существующий `/dev/log`: обе диагностические строки
  (`unclean shutdown`, `root fs was read-only at boot`) — то есть вся оставшаяся ценность модуля —
  молча терялись, файла на rootfs у нас больше нет.
- **Активный сервер переехал из UCI в `/etc/monkey-business/active`.** Это рантайм-состояние, а не
  выбор пользователя: в UI нет действия «выбрать этот сервер», приоритет задаётся порядком секций.
  Раньше каждый автофейловер делал `uci commit`, переписывая `/etc/config/monkey-business` целиком.
  Теперь запись идёт только при РЕАЛЬНОЙ смене тега.
- **`applyConfig` не пишет байт-в-байт тот же конфиг** и не зовёт `sync`. В фазе `down` watchdog
  зовёт `config_apply` раз в `BACKOFF`, и когда рабочих серверов нет, `selectWorking` каждый раз
  возвращает один и тот же `servers[0]` — без этой проверки один и тот же файл ложился бы на карту
  144 раза в сутки, то есть заменил бы собой убранный `beat`.

## Миграция уже прошитых устройств
Деплой сохраняет старый `/etc/config/monkey-business`, поэтому одной выкладки файлов мало:

- строка `*/5 … boothealth.sh beat` **активно вычищается** из `/etc/crontabs/root`;
- `uci.selected.server` **переливается** в `/etc/monkey-business/active`, после чего секция
  `selected` удаляется. Без переливки дашборд показал бы «Server: none» бессрочно: в фазе `healthy`
  watchdog не зовёт `config_apply`, и файл не появился бы, пока пользователь сам не нажмёт Apply.

## Следствия
- Любая новая запись на rootfs по таймеру/в цикле — регресс этого решения. Рантайм-состояние живёт в
  `/tmp`, лог — в syslog, персистентное пишется только при фактическом изменении содержимого.
- `uci.selected.server` больше нет: секция удалена из `root/etc/config/monkey-business`, watchdog
  читает `/etc/monkey-business/active` файлом.
- **Открытый хвост: atime.** Watchdog раз в минуту читает `/etc/monkey-business/active` и
  `/etc/config/monkey-business`. При дефолтном `relatime` это несколько записей инода в сутки —
  против 288 sync/сутки пыль, но формально «ноль периодических записей» держится только при
  `noatime`. Проверять на устройстве: `grep ' / ' /proc/mounts`. Монтирование автоматически НЕ
  меняем — это отдельное решение, а не побочный эффект этого.
- **Открытый хвост: ранний выход `applyConfig` не проверен на железе.** По коду procd
  (`instance_update`: `!changed && running` → no-op, не running → `instance_start`) мёртвый xray
  поднимется, но это вывод из чтения исходников, а не запуск. До первого боевого деплоя нужен T3:
  (1) Apply тем же конфигом при живом xray → PID не меняется, kill-switch на месте; (2) `kill -9
  xray` + Apply тем же конфигом → поднялся; (3) Turn off → Turn on → поднялся; (4) Apply со сменой
  сервера → PID сменился, `nft list ruleset` не пустел.
- Диагностика после ребута изменилась: `logread -e mb-event` вместо
  `tail -f /usr/local/server.main.log`. Обратная сторона — syslog не переживает перезагрузку, поэтому
  причина последнего падения по логу больше не восстанавливается. Осознанный размен: лог, ради
  которого умирает носитель, дороже лога, которого нет.
