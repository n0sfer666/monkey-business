# 2026-10-08 — Событийная запись `active_sub` при автопереключении подписки

## Контекст
Несколько подписок (`specs/2026-10-08-multi-subscription.md`): одна активная, остальные — резерв.
Активная подписка может умереть без участия человека: кончился трафик (`used >= total` из userinfo)
или срок (`now >= expire`). Туннель через неё мёртв, watchdog уйдёт в резерв, но `active_sub`
останется указывать на мёртвую — после ребута, Apply или тумблера выбор снова начнётся с неё.

`decisions/2026-07-26-zero-periodic-writes.md` запрещает периодические записи на rootfs: SD-карта
R2S умирала от записей по таймеру в одни и те же LBA. Проверка «активная мертва?» по природе
периодическая (cron 1/мин в `subupdate.sh`), а `active_sub` живёт в `/etc/config/monkey-business`.

## Решение
`global.active_sub` при автопереключении пишется в UCI **только на событии** — смене мёртвой
активной на живую:

- проверка идёт каждый тик, но только читает UCI;
- запись — если активная мертва И есть живая альтернатива (следующая по порядку, по кругу);
- нет живой альтернативы — записи нет, на каждом следующем тике тоже;
- обратного автопереключения нет: вернуть продлённую подписку может только человек.

Число записей ограничено числом смертей подписок: чтобы автопереключение сработало снова,
должна умереть уже новая активная — это внешнее событие у провайдера, а не тик таймера. Пинг-понга
нет: уход возможен только с мёртвой на живую, а возврат требует смерти той, на которую ушли.

Причина переключения (для плашки на дашборде) — в tmpfs (`/tmp/mb-subupdate/autoswitch`), не в UCI:
это рантайм-сообщение, его потеря при ребуте безвредна.

### Почему UCI, а не tmpfs
`active_sub` — выбор человека, а не рантайм-состояние (в отличие от `/etc/monkey-business/active`,
куда пишет failover). Автопереключение подменяет этот выбор осознанно: держать его в tmpfs значит
после ребута снова начинать с мёртвой подписки и переключаться заново — та же запись, только на
каждой загрузке.

## Отвергнуто
- **Только резерв без записи** (watchdog уходит в резерв, `active_sub` не трогаем): каждый Apply,
  тумблер и ребут начинаются с перебора мёртвой подписки — до минуты на пробы, а на исчерпанной
  панель может ещё и пускать handshake без трафика.
- **Запись при каждой проверке**: ровно тот регресс, против которого `zero-periodic-writes`.

## Следствия
- Любой код, пишущий `active_sub` не по действию человека, обязан сохранять инвариант «только при
  фактической смене на живую»; регрессионный тест — повторный тик с мёртвой активной без живых
  альтернатив не вызывает записи.
- Автопереключение может молча увести трафик к другому провайдеру — поэтому плашка на дашборде
  обязательна, а обратного автопереключения нет.
