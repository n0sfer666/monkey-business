# Несколько подписок

## Контекст
Сейчас подписка одна: секция `subscription 'subscription'`, серверы — плоский список анонимных
`server` (у подписочных `source=subscription`, у ручных source нет или `manual`). Порядок секций =
приоритет, `selectWorking` перебирает его сверху и пишет тег первого живого в
`/etc/monkey-business/active`. Главный сценарий второй подписки — запасной провайдер, когда первого
режет DPI или кончился трафик (память mb-failover).

Наивное «N секций вместо одной» ломает пять вещей: merge подписки A стирает серверы B; одинаковые
теги двух провайдеров неразличимы для `selectedServer`/ping; анонимные `cfgXXXXXX` нестабильны как
ссылка; удаление подписки формой оставляет её серверы; `subupdate.sh` знает одну секцию.

Score ≈ 65 (несколько модулей, данные в UCI, failover = критичный путь): независимое ревью и
регрессионные тесты обязательны.

## Решения
1. **Модель A: активная + автоматический резерв.** `global.active_sub` — выбор человека. Кандидаты
   `selectWorking`: [серверы активной + ручные, в drag-порядке] → [серверы остальных живых подписок,
   по порядку подписок]. Уход watchdog-failover в резерв `active_sub` НЕ переписывает; fail-back нет.
2. **Переключение** — селект `Subscription` в блоке Status дашборда, только при ≥ 2 подписках;
   мгновенный apply по паттерну `set_mode` (запись → apply → откат при ошибке; VPN выключен —
   только запись).
3. **Ручные серверы общие** для всех подписок, позиция — drag-порядок.
4. **Автопереключение** истёкшей/исчерпанной АКТИВНОЙ подписки на следующую живую — событийная
   запись в UCI, см. `decisions/2026-10-08-active-sub-event-write.md`.

Отвергнуто: B «строго активная» (резерв требует ручного переключения ровно тогда, когда интернета
нет), C «общий пул» (переключение = перетаскивание десятков строк).

## Модель данных
- **Подписка** — секция типа `subscription`. Новые — именованные `sub_<hex>` (имя генерирует LuCI в
  `handleAdd`), человекочитаемое имя — опция `name`. Существующая `subscription 'subscription'` —
  первая подписка с id `subscription` (`LEGACY_SUB`). Опции прежние: `url`, `auto_update`,
  `update_interval`, `used_upload`, `used_download`, `total`, `expire`.
- **Сервер** получает опцию `sub` = id подписки. Ручной (`source != subscription`) `sub` не имеет.
- **Легаси-атрибуция при чтении:** `source=subscription` без `sub` → `sub = LEGACY_SUB`. Делается в
  `reviveServer`, логика — `serverSub()` в `src/lib/subs.uc` (одно место для merge, выбора, UI).
  Записывается на диск при следующем `storeServers` — отдельной миграции нет.
- **Сироты:** серверы с `sub`, которой нет среди секций `subscription`, при чтении игнорируются
  (не кандидаты, не в UI) и выпадают при следующей записи списка.
- **`global.active_sub`**: нет/пусто/указывает на несуществующую секцию → первая подписка по порядку.

## Merge по срезу
`mergeKeepingOrder(existing, fresh, id)`: свежие серверы получают `sub = id`.
- Ручные — на своих позициях; свежий сервер с тем же `connectionKey`, что у ручного, не добавляется.
- Серверы ДРУГИХ подписок — нетронутыми на своих позициях (корень дефекта №1).
- Серверы среза `id` — матч по `serverKey`, данные из свежего ответа, позиция прежняя; пропавшие из
  ответа удаляются; новые — в конец списка (группировка по подпискам делается при выборе
  кандидатов, абсолютная позиция между группами значения не имеет).
- Дедупликации между подписками нет: одинаковый сервер у двух провайдеров — два кандидата.

## Идентичность активного сервера
`/etc/monkey-business/active` хранит `<sub>/<tag>` для подписочного и `<tag>` для ручного.
Строка никогда не парсится — только сравнивается с идентичностью, вычисленной из сервера, поэтому `/`
в теге не мешает. Watchdog хэширует файл `cksum` как непрозрачную строку (`watchdog.sh`
`selected_tag`, `recovery.sh` `WD_TAGSIG`) — формат для него безразличен. Переходный случай: файл
от старой версии содержит голый тег подписочного сервера → матч по тегу первого совпавшего (как
сейчас); первая же запись приводит к новому формату. Ping и `servers_list` ключуются той же
идентичностью.

## Автопереключение (решение 4)
- Мёртвая подписка: `total > 0 && used_upload + used_download >= total` (известно только из
  userinfo после fetch) ИЛИ `expire > 0 && now >= expire` (по времени).
- Триггер — `subupdate.sh` на каждом тике (cron 1/мин) после цикла обновлений зовёт rpcd-метод
  проверки. Метод читает UCI; пишет `global.active_sub` ТОЛЬКО если активная мертва и есть живая
  альтернатива (следующая по порядку, по кругу). Нет живых — ничего не пишет.
- После записи — `configApply` сразу при включённом VPN: туннель на исчерпанной подписке и так мёртв.
- Причина пишется в tmpfs (`/tmp/mb-subupdate/autoswitch`: `<from> <reason>`); дашборд показывает
  «переключено автоматически: A исчерпана»; ручное переключение файл стирает.
- Обратного автопереключения нет: продлённую A человек возвращает сам.
- Мёртвые подписки в резерве не кандидаты `selectWorking`.

## subupdate.sh
Цикл по секциям `subscription`: у каждой свой `auto_update`/`update_interval`, состояние
`/tmp/mb-subupdate/<id>`, провал одной не блокирует остальные. ubus `subscription_update` получает
`{ "sub": "<id>" }`; без `sub` — `LEGACY_SUB` (совместимость с кнопкой старого UI).

## UI
Принцип: при одной подписке UI выглядит как сейчас.
- Дашборд, Status: `Subscription: [A ▾]` над `Server:` при ≥ 2 подписках; в той же строке —
  «сейчас резерв: B», если трафик идёт через неактивную; мёртвые подсвечены в селекте.
- Servers: NamedSection → TypedSection подписок (Name / URL / Auto-update / Interval / Fetch,
  Add/Delete). Таблица серверов — read-only колонка Subscription.
- Дашборд: таблица серверов в реальном порядке кандидатов (активная группа, затем резерв).
- Плашка трафика — по подписке, через которую идёт трафик.

## Миграция и откат
Миграции нет: правило легаси-атрибуции + `active_sub` по умолчанию = первая подписка. uci-defaults
не нужен. Откат на старый пакет безопасен: лишние опции (`sub`, `name`, `active_sub`) старый код
игнорирует; `active` с `<sub>/<tag>` старый код не найдёт и сделает `selectBest` — сервер по
приоритету, туннель поднимется. Серверы второй подписки старый merge сотрёт при первом обновлении —
приемлемо для отката.

## План (4 коммита)
1. **Модель + merge.** `src/lib/subs.uc` (`LEGACY_SUB`, `isManual`, `serverSub`), `sub` в
   `reviveServer`, merge по срезу. Тесты: merge не трогает чужой срез и ручные, легаси без `sub`
   приписывается `subscription`, свежие получают `sub`, ручной не получает.
2. **Выбор и переключение.** ctx `getSubscriptions()`/`getSubscription(id)`/`setActiveSub(id)`,
   кандидаты по группам, сироты, идентичность `<sub>/<tag>`, rpc `subscription_select`,
   `servers_list`/`status` с `sub`/`active_sub`/резервом, трафик подписки трафика. Тесты: порядок
   кандидатов, коллизия тегов, сироты, откат select при ошибке apply, легаси-файл `active`.
3. **subupdate + автопереключение.** Цикл по секциям, `subscription_update {sub}`, метод проверки и
   автопереключения. Тесты: subupdate_test (цикл, независимые состояния, провал одной), rpcd
   (исчерпана/истекла → следующая живая; нет живых → без записи; повторный тик — без записи).
4. **UI + доки.** servers.js, status.js, traffic.js, serverlist.js, dashboard.js, acl.d, конфиг-
   дефолт, README/docs EN+RU, runbook ручной проверки на R2S.

## DoD
- N подписок: добавить/удалить/переименовать на Servers; старый конфиг работает без миграции.
- Обновление (кнопка и cron) каждой подписки независимо, не трогает чужие и ручные серверы.
- Переключение с дашборда применяется сразу, откат при ошибке, при выключенном VPN — только запись.
- Failover по модели A; дашборд честно показывает, через какую подписку идёт трафик.
- Автопереключение мёртвой активной; запись в UCI только на событии.
- При одной подписке UI визуально как сейчас.
- `make lint`, `make check`, `make test-unit`, `make test-integ` зелёные; регрессионные тесты на
  все пять дефектов наивной реализации.
- Ревью `code-reviewer` на каждый коммит; runbook ручной проверки обновлён в коммите 4.

## Проверка
T1+T2 (линтер, unit/integ), T4 (регрессия merge/коллизий/автопереключения). T3 — пользователь на R2S
по runbook: две подписки, переключение с дашборда, failover в резерв, автообновление обеих,
автопереключение при истёкшей `expire`.

## Риски
- Гонка автопереключения с watchdog: оба могут позвать `config_apply`. Смена `active` не нашим
  failover'ом для watchdog = ручной выбор (сброс фазы и backoff) — для смены провайдера это
  желаемо, но одновременный apply проверить в коммите 3.
- Резерв удлиняет перебор `selectWorking`: `failover_cap` и `FAILOVER_RESERVE`
  (`decisions/2026-07-28-down-phase-failover-budget.md`) считаются по всему списку кандидатов —
  пересчитать бюджет при ≥ 2 подписках в коммите 2.
