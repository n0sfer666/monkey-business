# Спецификация: monkey-business — VPN-клиент для ImmortalWrt/OpenWrt

> Аналог passwall/v2rayA с современными технологиями обхода блокировок (Reality + VLESS + XHTTP)
> и минималистичным интерфейсом. Целевое железо — NanoPi R2S (RK3328, aarch64).

## Контекст

Пользователь хочет собственный VPN-клиент для роутера на ImmortalWrt (совместимый с OpenWrt),
заменяющий passwall/v2rayA более простым UI. Провайдер — VPNON (раздаёт серверы через подписку),
но нужна и ручная конфигурация серверов. Разработка разбита на 4 этапа (см. ниже).

Целевое устройство: NanoPi R2S — RK3328, ARMv8 (aarch64), 2×Ethernet (один через USB3), ~1 ГБ RAM,
без аппаратного AES. Роль в сети — **основной шлюз всей LAN**.

### Этапы разработки

1. **Dev-среда** — эмуляция ImmortalWrt aarch64 в QEMU для быстрой итерации UI/логики;
   финальные сетевые и перф-тесты на реальном R2S.
2. **Болванка с LuCI** — минималистичный интерфейс, подвязанный к мок-серверу
   (захваченный реальный ответ VPNON как фикстура). Подписка VPNON + ручное добавление серверов.
   Без реальных подключений, но всё максимально близко к боевой реализации.
3. **Боевая система** — реальное подключение к серверам, туннелирование трафика
   (VPN/direct по geoip.dat/geosite.dat). **Перед этим этапом взять у пользователя реальную ссылку**
   (получена заранее, см. «Открытые вопросы» — использовать только на этапе 3).
4. **Тонкости** — direct/remote DNS, DNS-over-HTTPS, anti-DPI (uTLS + XHTTP padding).
   Настройка на едином экране с advanced-секциями, каждая опция с подсказкой «для чего она нужна».

## Требования

### Функциональные

- **Движок прокси**: Xray-core на этапе 3. Генератор конфига абстрагировать так, чтобы
  в будущем подключить sing-box вторым бэкендом без переписывания UI.
- **Протоколы**: VLESS + Reality + XHTTP (референсная реализация в Xray-core).
- **Источники серверов**:
  - подписка VPNON (URL с токеном; авто-определение формата парсером);
  - ручное добавление сервера (вставка `vless://` URI или поля формы).
- **Маршрутизация**: режим по умолчанию — bypass локального (RU/CN) → остальное через VPN.
  Локальный регион и приватные сети идут direct по geoip/geosite, всё прочее — в туннель.
- **Failover**: ручной выбор сервера с уведомлением при отказе текущего (без авто-переключения в MVP).
- **Дашборд** (минимализм): статус подключения + тумблер on/off + текущий сервер;
  ping/latency по серверам с подсказкой лучшего. Без realtime-графиков и логов на главном экране.
- **DNS** (этап 4): split — direct-DNS для RU-доменов, DoH через VPN для остального.
- **Anti-DPI** (этап 4): uTLS fingerprint (chrome/firefox) + XHTTP padding.
- **IPv6**: опция, по умолчанию блокировать IPv6 на LAN (защита от утечки мимо туннеля).
- **Kill-switch**: опция, по умолчанию fail-closed (блокировать VPN-трафик при обрыве туннеля).
- **Обновление подписки**: авто по расписанию (cron) + ручная кнопка; при ошибке/пустом
  ответе сохранять предыдущий список (не обнулять).
- **Geo-данные**: скачивать geoip.dat/geosite.dat при установке + кнопка «обновить».
- **Первый запуск**: единый экран настройки с advanced-секциями и tooltip у каждой опции.

### Нефункциональные

- **Производительность**: целевой throughput ~100–300 Мбит/с на R2S (реалистичный потолок
  RK3328 без аппаратного AES при Reality/VLESS). Критерий приёмки — не ниже нижней границы.
- **Платформа**: ImmortalWrt (приоритет) + совместимость с OpenWrt. Target — aarch64 (RK3328).
- **Firewall**: интеграция с fw4/nftables (современный OpenWrt). Без зависимости от legacy iptables.
- **Локализация**: русский первичный + английский (стандартный i18n LuCI).
- **Безопасность хранения**: файлы с кредами (токен подписки, ключи Reality) — права 0600;
  секреты не логировать и маскировать в UI.
- **Дистрибуция**: ipk-пакеты через OpenWrt SDK + раздача через GitHub Releases (`opkg install`).
- **Размер**: укладываться в ограничения flash R2S (geo-данные не бандлить в ipk).

## Архитектура

### Слои

```
┌─────────────────────────────────────────────┐
│  LuCI client-side JS (luci-base + ubus/rpcd) │  ← минималистичный UI, i18n
├─────────────────────────────────────────────┤
│  ubus/rpcd сервисы (статус, ping, apply)     │  ← API между UI и бэкендом
├─────────────────────────────────────────────┤
│  UCI (/etc/config/monkey-business)           │  ← источник правды конфигурации
├─────────────────────────────────────────────┤
│  Генератор конфига (UCI → Xray JSON)         │  ← абстрагирован под будущий sing-box
├─────────────────────────────────────────────┤
│  procd init-скрипт (запуск/перезапуск Xray)  │
├─────────────────────────────────────────────┤
│  Xray-core + nftables (TPROXY) + dnsmasq     │  ← движок, перехват, DNS
└─────────────────────────────────────────────┘
```

### Ключевые решения

- **Стек UI**: client-side JS LuCI (современный, чистый под минимализм; данные через ubus/rpcd).
- **Источник правды**: UCI → генератор JSON. Пользователь правит UCI через LuCI,
  скрипт генерирует Xray JSON при apply. Нативно для OpenWrt, бэкап через sysupgrade.
- **Перехват трафика**: TPROXY на nftables (прозрачный TCP+UDP через mark+TPROXY),
  гибкая маршрутизация по доменам/geoip, интеграция с fw4.
- **Движок**: Xray-core. Генератор конфига изолирован за интерфейсом, чтобы добавить sing-box позже.
- **Роль роутера**: основной шлюз LAN — полная интеграция с fw4/DHCP/DNS.

### Подписка (парсер)

- Парсер с авто-определением формата: base64-список `vless://` URI / Clash YAML / sing-box JSON.
- Под реальную ссылку VPNON формат уточняется на этапе 3 (см. «Открытые вопросы»).
- Для этапа 2 — захватить реальный ответ VPNON один раз как фикстуру мок-сервера.

## API / Интерфейсы

- **ubus/rpcd** методы (черновик):
  - `status` — состояние подключения, текущий сервер, аптайм.
  - `servers.list` — список серверов (из подписки + ручные).
  - `servers.ping` — измерить latency по серверам.
  - `subscription.update` — обновить подписку (ручная кнопка).
  - `geo.update` — обновить geoip/geosite.
  - `config.apply` — сгенерировать JSON и перезапустить Xray.
  - `service.toggle` — вкл/выкл туннель.
- **UCI-схема** `/etc/config/monkey-business`: секции `global`, `subscription`, `server`,
  `routing`, `dns`, `anti_dpi`.

## UI/UX

- **Главный экран**: большой тумблер on/off, статус, текущий сервер, список серверов с ping
  и подсказкой лучшего.
- **Серверы**: подписка (URL, кнопка обновить, авто-расписание) + ручное добавление.
- **Настройки (единый экран, advanced-секции)**: routing-режим, DNS (split/DoH),
  anti-DPI (uTLS + padding), IPv6, kill-switch. Каждая опция — tooltip «для чего она нужна».
- **Язык**: RU по умолчанию, EN через i18n.
- **Принцип**: проще passwall — разумные default, тонкости спрятаны, но доступны с пояснениями.

## Edge Cases

- Подписка недоступна / пустой ответ / истёкший токен → сохранить старый список, показать ошибку.
- Текущий сервер не отвечает → уведомить, дать ручной выбор.
- Обрыв туннеля → fail-closed (по умолчанию) блокирует VPN-трафик.
- IPv6-трафик клиентов → блокируется по умолчанию (нет утечки).
- DNS-запросы → split не должен «протекать» реальными запросами для зарубежных доменов.
- geo-файлы не скачались при установке → деградация маршрутизации, нужен явный статус/кнопка.
- Нехватка flash при скачивании geo → проверять место, понятная ошибка.
- Перезагрузка/sysupgrade → конфиг и креды переживают (UCI в keep-списке).
- Xray упал/не стартует → procd respawn + отражение ошибки в статусе и логах.
- Reality handshake fail (неверный SNI/publicKey/shortId) → диагностируемая ошибка.

## Риски и митигации

| Риск | Вероятность | Митигация |
|------|-------------|-----------|
| Throughput ниже целевого на RK3328 | Высокая | Замер на железе (T3), тюнинг XHTTP/mux/sniffing, реалистичный целевой диапазон 100–300 Мбит/с |
| Утечка реального IP при обрыве | Средняя | Kill-switch fail-closed по умолчанию + тест «убить xray» |
| Утечка через IPv6 | Средняя | Блокировка IPv6 на LAN по умолчанию |
| DNS-утечка/подмена | Средняя | Split DNS (RU direct / DoH в туннеле), leak-тест |
| Несовместимость формата подписки VPNON | Средняя | Парсер с авто-определением, проверка на реальной ссылке (этап 3) |
| Сложность TPROXF+fw4 на основном шлюзе | Средняя | Тестировать интеграцию с fw4 рано, на dev-среде QEMU aarch64 |
| Разница QEMU vs реальный R2S (aarch64-специфика) | Средняя | Финальные сетевые/перф-тесты на железе |
| Раздувание flash из-за geo-файлов | Средняя | Скачивание при установке, не бандлить в ipk |
| Lock-in под Xray | Низкая | Генератор конфига абстрагирован под будущий sing-box |
| Перф realtime-статы грузит CPU | Низкая | Дашборд минималистичный, без realtime-графиков |

## Тестовая стратегия

### Инструментарий (решения)

- **Backend-логика** (парсер подписки, генератор UCI→Xray JSON, rpcd-хендлеры): **ucode**.
  Интерпретатор запускается на хосте → быстрые unit-тесты без QEMU/железа.
- **Unit-тесты**: минимальный ucode-харнесс (assert-хелперы + раннер) + фикстуры/golden JSON.
- **Интеграционные тесты** (routing/leak/kill-switch/DNS): харнесс на **Linux network namespaces**
  (bash + `ip netns` + `nft` + xray + контролируемый upstream/локальный Reality-сервер).
- **Среда прогона**: macOS не имеет netns/nftables/ucode → unit и netns-тесты гоняются в
  **Linux-контейнере** (Docker/colima, привилегированный для netns). Цели в `Makefile`.
- **CI**: пока локально (`make test-unit`, `make test-integ`, `make lint`, `make package`).
  GitHub Actions — позже.
- **Lint**: `ucode -c` (синтаксис), `shellcheck` (shell), eslint (LuCI JS).

### Уровни по шагам

- **T1 (Static)**: типы/линтер, reasoning по edge-кейсам генератора и парсера.
- **T2 (Run)**: сборка ipk, запуск Xray с сгенерированным JSON, проверка валидности конфига;
  смоук-загрузка dev-VM в QEMU.
- **T4 (Test, регресс)**: unit/snapshot-тесты парсера подписки и генератора UCI→JSON на фикстурах
  (на хосте/в контейнере, без железа) — пинят корректность маппинга.
- **T3 (Deep, netns-харнесс; финал на реальном R2S / QEMU)**:
  - **Leak-тест**: внешний IP/DNS через туннель — IP должен быть VPN, RU-домены direct.
  - **Routing-тест**: RU-ресурсы идут direct, зарубежные — через VPN (проверка geoip/geosite).
  - **Kill-switch тест**: остановить Xray → fail-closed реально блокирует, нет утечки.
  - **DNS-тест**: split резолвит RU напрямую, зарубеж через DoH в туннеле.
  - **IPv6-тест**: IPv6-трафик клиентов заблокирован (нет утечки).
- Перф-замер throughput — на реальном R2S как критерий приёмки (blocked: нужно железо).

### Переосмысление тестов между шагами

Каждый шаг, меняющий поведение/контракт предыдущего, **обязан** ревизовать его тесты:
- Изменилась схема нормализованного сервера (парсер) → обновить golden-фикстуры генератора.
- Расширился генератор (DNS/anti-DPI/IPv6 на этапе 4) → обновить snapshot-фикстуры и netns-проверки.
- Изменился UCI-контракт → обновить rpcd-хендлеры и их тесты.
Правило фиксируется в плане: у каждой задачи есть секции «тесты добавить» и «тесты ревизовать».

### Границы автономного исполнения (blocked)

Не выполнимо автономно (готовятся скрипты+инструкции, помечаются blocked):
- прошивка/перф-тесты на реальном NanoPi R2S (нужно железо);
- боевое подключение к VPNON и захват реального ответа подписки (нужна секретная ссылка, этап 3);
- визуальная проверка LuCI UI на работающей VM (нужна запущенная dev-VM).

## Открытые вопросы

- **Реальная ссылка подписки VPNON** получена заранее и хранится у пользователя.
  Использовать **только на этапе 3** (и однократно — для захвата фикстуры мок-сервера на этапе 2).
  Точный формат подписки определить по ней; до этого парсер делать универсальным.
- Конкретные параметры Reality (SNI, publicKey, shortId, flow) приходят из подписки/ручного ввода —
  уточнить набор полей по реальному ответу VPNON.
- Точное расписание авто-обновления подписки (раз в сутки по умолчанию — подтвердить).
- Список upstream DoH-резолверов по умолчанию.
